## Notes
In **Chapter 10: Generic Types, Traits, and Lifetimes**, *The Rust Programming Language* introduces the core mechanisms Rust uses to handle code duplication, enforce behavioral contracts, and guarantee memory safety at compile time without incurring runtime performance penalties.

---

### **1. Generic Data Types**

Generics are abstract stand-ins for concrete types or other properties. They allow developers to define functions, structs, enums, and methods that operate on multiple data types.

#### **A. Generics in Function Definitions**
When code logic is identical across multiple types (such as finding the largest item in a slice of `i32` vs. `char`), generics parameterize the function signature. Type parameters are declared inside angle brackets (`<T>`) before the function's parameter list.

##### **Generic Function Definition Example**
```rust
// T is a generic type parameter (CamelCase by convention)
fn largest<T>(list: &[T]) -> T {
    let mut largest = list;

    for &item in list.iter() {
        if item > largest { // Note: requires comparison capabilities
            largest = item;
        }
    }

    largest
}
```
*(Source: Listing 10-5)*

*Note*: The above snippet fails to compile on its own because the greater-than operator (`>`) is not implemented for all possible types `T`. Rust requires **trait bounds** to restrict `T` to types that support comparison.

---

#### **B. Generics in Structs & Enums**
Structs and enums can use one or more generic type parameters inside angle brackets `<>`.

```rust
// Both fields x and y must have the EXACT SAME type T
struct Point<T> {
    x: T,
    y: T,
}

// x and y can have DIFFERENT types T and U
struct PointTwoTypes<T, U> {
    x: T,
    y: U,
}

fn main() {
    let integer = Point { x: 5, y: 10 };
    let float = Point { x: 1.0, y: 4.0 };
    let mixed = PointTwoTypes { x: 5, y: 4.0 };
}
```
*(Source: Listing 10-6, 10-7, 10-8)*

##### **Standard Library Generic Enums**
* **`Option<T>`**: Represents an optional value with variants `Some(T)` and `None`.
* **`Result<T, E>`**: Represents success (`Ok(T)`) or failure (`Err(E)`).

---

#### **C. Generics in Method Definitions**
You must declare generic parameters right after `impl` so Rust recognizes that the identifier in `Point<T>` is a generic type parameter rather than a concrete type.

```rust
struct Point<T, U> {
    x: T,
    y: U,
}

impl<T, U> Point<T, U> {
    // Method can declare additional generic parameters V and W
    fn mixup<V, W>(self, other: Point<V, W>) -> Point<T, W> {
        Point {
            x: self.x,
            y: other.y,
        }
    }
}
```
*(Source: Listing 10-11)*

You can also write `impl` blocks that target specific concrete types (e.g., `impl Point<f32>`), making methods available **only** to instances with those specific concrete types.

---

#### **D. Performance of Generics: Monomorphization**
Rust executes generic code with **zero runtime cost**. The compiler achieves this at compile time through **monomorphization**—the process of expanding generic definitions into specific implementations for every concrete type used in the code.

```rust
// Original code written by developer:
let integer = Some(5);
let float = Some(5.0);

// Code generated by compiler via monomorphization:
enum Option_i32 { Some(i32), None }
enum Option_f64 { Some(f64), None }

let integer = Option_i32::Some(5);
let float = Option_f64::Some(5.0);
```
*(Source: Monomorphization)*

### **2. Traits: Defining Shared Behavior**

A **trait** defines a set of method signatures that a type must fulfill to exhibit a shared behavior (similar to interfaces in other languages).

#### **A. Defining and Implementing a Trait**
```rust
// Defining a trait
pub trait Summary {
    fn summarize(&self) -> String;
}

pub struct NewsArticle {
    pub headline: String,
    pub location: String,
    pub author: String,
    pub content: String,
}

// Implementing a trait on a type
impl Summary for NewsArticle {
    fn summarize(&self) -> String {
        format!("{}, by {} ({})", self.headline, self.author, self.location)
    }
}
```
*(Source: Listing 10-12 & Listing 10-13)*

---

#### **B. The Orphan Rule (Coherence)**
Rust enforces the **orphan rule**: you can implement a trait on a type **only if either the trait or the type is local to your crate**.
* You **can** implement a standard trait like `Display` on a local struct (`Tweet`).
* You **can** implement a local trait (`Summary`) on a standard type (`Vec<T>`).
* You **cannot** implement an external trait (`Display`) on an external type (`Vec<T>`) within your crate. This rule guarantees that external crates cannot break each other's implementations.

---

#### **C. Default Implementations**
Traits can provide default method bodies. Implementors can keep or override default behaviors. Default methods can also call other required methods defined in the same trait.

```rust
pub trait Summary {
    fn summarize_author(&self) -> String;

    // Default implementation calling a required method
    fn summarize(&self) -> String {
        format!("(Read more from {}...)", self.summarize_author())
    }
}
```
*(Source: Default Implementations)*

---

#### **D. Trait Bounds & `where` Clauses**
To constrain a generic type parameter to types that implement specific traits, use **trait bounds**.

##### **Syntax Styles:**
1. **Inline Bound**:
   ```rust
   pub fn notify<T: Summary>(item: T) {
       println!("Breaking news! {}", item.summarize());
   }
   ```
   *(Source: Trait Bounds)*

2. **Multiple Trait Bounds (`+` Operator)**:
   ```rust
   pub fn notify<T: Summary + Display>(item: T)
   ```
   *(Source: Multiple Trait Bounds)*

3. **`where` Clause Syntax** (clears up cluttered signatures):
   ```rust
   fn some_function<T, U>(t: T, u: U) -> i32
       where T: Display + Clone,
             U: Clone + Debug
   {
       // Function body
   }
   ```
   *(Source: `where` Clauses)*

---

#### **E. Fixing the `largest` Function**
To enable finding the largest item in a generic slice, `T` must implement `PartialOrd` (for `>`) and `Copy` (to move values out of the slice). Alternatively, returning `&T` avoids needing `Copy` or `Clone`.

```rust
fn largest<T: PartialOrd + Copy>(list: &[T]) -> T {
    let mut largest = list;

    for &item in list.iter() {
        if item > largest {
            largest = item;
        }
    }

    largest
}
```
*(Source: Listing 10-15)*

---

#### **F. Conditional and Blanket Implementations**
* **Conditional Methods**: Methods can be implemented conditionally based on trait bounds.
* **Blanket Implementations**: Implementing a trait for *any* type that implements another trait (e.g., standard library implements `ToString` for any type that implements `Display`).

```rust
// Blanket implementation example from std
impl<T: Display> ToString for T {
    // ...
}
```
*(Source: Blanket Implementations)*

### **3. Validating References with Lifetimes**

Lifetimes are generic parameters that inform the compiler how references relate to each other, allowing the **borrow checker** to prevent dangling references at compile time.

#### **A. The Borrow Checker**
The compiler's borrow checker compares variable scopes (`'a` and `'b`) to ensure that referenced data lives at least as long as the reference pointing to it.

```text
{
    let r;                // ---------+-- 'a
    {                     //          |
        let x = 5;        // -+-- 'b  |
        r = &x;           //  |       |
    }                     // -+       |  ERROR: 'b is shorter than 'a!
    println!("r: {}", r); //          |
}                         // ---------+
```
*(Source: Listing 10-18)*

---

#### **B. Lifetime Annotation Syntax**
Lifetime annotations **do not change how long values live**; they describe the relationships between the lifetimes of multiple references. Lifetime parameter names start with an apostrophe (`'`) and are usually short and lowercase (e.g., `'a`).

```rust
&i32        // A reference
&'a i32     // A reference with an explicit lifetime 'a
&'a mut i32 // A mutable reference with an explicit lifetime 'a
```
*(Source: Lifetime Annotation Syntax)*

---

#### **C. Lifetime Annotations in Functions**
When returning a reference from a function, the return lifetime must match one of the input parameter lifetimes. Returning a reference created inside the function causes a compile error because it results in a dangling reference.

```rust
// 'a specifies that returned reference is valid for the smaller lifetime of x and y
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```
*(Source: Listing 10-22)*

---

#### **D. Lifetime Annotations in Struct Definitions**
If a struct stores references rather than owned types (like `String`), every reference in the struct definition requires a lifetime annotation. This guarantees that an instance of the struct cannot outlive the reference it holds.

```rust
struct ImportantExcerpt<'a> {
    part: &'a str,
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first_sentence = novel.split('.').next().expect("Could not find a '.'");
    let i = ImportantExcerpt { part: first_sentence };
}
```
*(Source: Listing 10-25)*

---

#### **E. Lifetime Elision Rules**
To avoid forcing developers to enter repetitive annotations in common scenarios, Rust applies three deterministic **lifetime elision rules** in function signatures:

1. **First Rule (Input Lifetimes)**: Every parameter that is a reference gets its own input lifetime parameter (e.g., `fn foo<'a, 'b>(x: &'a i32, y: &'b i32)`).
2. **Second Rule (Output Lifetimes)**: If there is exactly **one** input lifetime parameter, that lifetime is assigned to all output parameters (e.g., `fn foo<'a>(x: &'a i32) -> &'a i32`).
3. **Third Rule (Method Signatures)**: If there are multiple input lifetime parameters, but one of them is `&self` or `&mut self`, the lifetime of `self` is assigned to all output lifetime parameters.

If ambiguity remains after applying these rules, the compiler halts with an error requiring explicit lifetime annotations.

---

#### **F. The `'static` Lifetime**
The **`'static`** lifetime denotes references that are valid for the entire duration of the program execution. All string literals possess the `'static` lifetime because their text is stored directly inside the compiled binary.

```rust
let s: &'static str = "I have a static lifetime.";
```
*(Source: The Static Lifetime)*

### **4. Combining Generics, Trait Bounds, and Lifetimes**

All three constructs can be combined in a single function signature. Lifetime parameters go in the same angle bracket list alongside generic type parameters before any `where` clause.

```rust
use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(
    x: &'a str,
    y: &'a str,
    ann: T,
) -> &'a str
where
    T: Display,
{
    println!("Announcement! {}", ann);
    if x.len() > y.len() {
        x
    } else {
        y
    }
}
```
